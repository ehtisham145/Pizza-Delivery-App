⚙️ Status Flow Rules — Very Important
pending → confirmed → preparing → out_for_delivery → delivered
                                                    ↑
                          cancelled (only from pending)
•	Staff can only move status forward — never backward
•	Customer can only cancel when status is pending
•	Once delivered, status is frozen — nobody can change it
•	Every status change should trigger a notification to the customer
________________________________________
⚙️ Business Logic Rules
•	On POST /orders — copy everything from cart into OrderItems as snapshots
•	Store pizza_name, size_name, topping_name as plain strings — not FKs — because menu can change later
•	Cart must not be empty when placing order — return 400
•	Address must belong to the logged-in user — validate this
•	After order is created, clear the cart and create a Payment record simultaneously
•	total_price on Order = sum of all OrderItem subtotals
________________________________________
📦 Pydantic Schemas
•	PlaceOrderSchema — address_id, payment_method, notes (optional)
•	OrderStatusUpdateSchema — new_status (validated against allowed transitions)
•	OrderItemResponseSchema — pizza_name, size, toppings, quantity, subtotal
•	OrderResponseSchema — id, status, total, items, address, payment info, created_at
________________________________________
❌ Common Mistakes to Avoid
•	Using FKs for pizza/topping names in OrderItem — always snapshot as strings
•	Allowing status to go backward
•	Not validating that the address belongs to the customer
•	Not clearing the cart after order is placed
•	Forgetting to create the payment record on order creation
